2. Root-cause analysis

Requires renderer/layout change

  • Every node is fixed at 105×54 or 145×54 regardless of content.
  • All node and group positions are absolute.
  • Cubic edges are calculated only from node origins, not obstacles or ports.
  • No crossing minimisation, hierarchical layout, compound layout or label-aware routing.
  • Edge-label backgrounds use a fixed 84×16 box.
  • Marker IDs a and g repeat across SVGs.

Requires information redesign

  • One eight-node template is imposed on flows, states, feedback loops and research decisions.
  • Long failure prose is sliced at 58 characters rather than moved outside the visual.
  • Actor, artifact, state and decision concepts share one visual grammar.
  • Several visuals exceed the useful 7±2 concept range at default fit.
  • Overview and implementation detail are mixed.

Can be fixed in shared CSS/wrapper

  • The surrounding .diagram forces a minimum SVG width of 760px.
  • The fixed 1040-wide viewBox scales text rather than reflowing layout.
  • No responsive height policy or ResizeObserver exists.
  • No isolated toolbar, focus model, print state or error fallback exists.
  • Current text alternatives are useful and should be retained.

Font reduction is rejected. The core failure is that text metrics are not inputs to layout. A new renderer must measure labels before routing, while information-design rules must keep the graph understandable at fit-to-view.

Why the other candidates are not selected

ELK.js alone

Excellent compound and orthogonal layout, but its own project states it provides no rendering or styling. Direct adoption would require building the renderer, text measurement and export layer—the custom engine this task forbids.

Cytoscape.js

Strong interactive graph canvas and layouts, but document-style native SVG export, wrapped text, sequence diagrams and print/accessibility require extensions or workarounds. Better for graph exploration than architecture documentation.

JointJS

Technically capable, including pan/zoom and export, but advanced export/scroller guidance is concentrated in JointJS+ and recent React-oriented APIs. It adds model/view authoring and licensing review beyond this document’s needs.

D2

Excellent language and exports, but official docs still describe browser inclusion instructions as work in progress. Its SVG may use foreignObject, and PNG uses Playwright in the CLI path.

Structurizr

C4 concepts are valuable, but adopting its workspace/toolchain for a standalone, multi-category HTML document is disproportionate. Use C4 scope and naming discipline, not Structurizr as the browser implementation.

SVG.js/custom

It can draw and manipulate SVG, but it does not solve automatic layout, routing or label placement. It would preserve the present geometry burden under a different API.

4. Recommended approach and ownership boundary

Primary: Mermaid

  • Use flowchart + ELK for ordinary architecture, component, data-flow and dependency diagrams after qualification.
  • Use Mermaid-native sequence and state syntax for those categories.
  • Avoid Mermaid C4 syntax while it remains marked experimental; express C4 scope with ordinary subgraphs, naming and legends.
  • Set securityLevel:'strict', htmlLabels:false, deterministic IDs and native SVG text.

Fallback: Viz.js / Graphviz

  • Use only when compound clusters, cross-hierarchy edges or orthogonal routing fail Mermaid acceptance.
  • DOT source remains declarative; dot auto-sizes nodes and clusters and emits standalone SVG.
  • Do not use Graphviz for sequence diagrams or simple flows merely because it is available.
  • Fallback approval is per diagram and recorded in the registry.

Renderer ownership is exclusive by category. The wrapper never calculates node or edge geometry. ELK is a layout implementation selected through Mermaid, not a public diagram authoring surface.

5. Zoom, pan and export design

Consistent viewport contract

  • Toolbar controls: zoom in/out, fit, reset, optional full screen, export SVG; all are real labelled buttons.
  • Mouse wheel/trackpad zoom only while pointer is inside the viewport; prevent page scroll only when consuming the gesture.
  • Blank-canvas drag pans; interactive SVG links retain click behavior.
  • Minimum 0.25×, maximum 4×, 1.2 step; fit is calculated from rendered content.
  • Reset returns to the initial fitted/centred state, not blindly to matrix identity.
  • Resize preserves the camera after user interaction; fit again only on explicit action.
  • Touch pinch is qualified separately; the selected utility has open touch issues, so touch is a release gate rather than an assumed feature.

SVG export algorithm

  1. Select only the registry-owned SVG.
  2. Clone it; strip scripts, event attributes, pan/zoom controls and the live viewport transform.
  3. Require native SVG text; reject or flatten foreignObject.
  4. Copy computed presentation properties into inline styles and replace CSS variables with computed values.
  5. Namespace every id and rewrite url(#…), marker, mask, clip-path and href references.
  6. Set xmlns, stable viewBox and intrinsic width/height.
  7. Serialize, parse once more, sanitize, then download <diagram-id>.svg.
  8. Open the exported file independently in Chromium, Firefox and an SVG editor during qualification.

PNG secondary path

Serialize the qualified SVG, load it into a same-origin Blob image, draw to a canvas at 2× device-independent dimensions, then use canvas.toBlob('image/png'). This remains secondary because browser font/image restrictions, canvas tainting and very large diagrams make raster export less dependable.

Rollback strategy
  • One commit per diagram ID; never mix infrastructure removal with diagram conversion.
  • Registry stores legacyRef and screenshot checksum through Phase 4.
  • A feature flag or query parameter selects legacy/new during pilot evaluation.
  • Failure to render, export or pass acceptance automatically displays the text alternative and legacy reference.
  • Rollback is a normal revert of one diagram-source commit; shared infrastructure remains while any migrated diagram uses it.

9. Diagram-specific acceptance checklist
  • No text overlaps a node, edge, label or control.
  • No text is unintentionally clipped.
  • Nodes size to measured content within category width rules.
  • Groups wrap content with standard padding.
  • Crossings are minimised and manually reviewed.
  • Edge labels remain readable at fit.
  • Default fit communicates primary structure.
  • Zoom/pan respect limits and do not scroll the page unexpectedly.
  • Fit and reset return deterministic views.
  • Resize updates without losing an intentional camera.
  • SVG export opens independently with text, markers and styles intact.
  • Multiple diagrams have no duplicate-ID/reference failures.
  • No console error or rejected promise.
  • Source remains understandable to a future editor.
  • Toolbar is keyboard operable and focus is visible.
  • SVG has accessible title/description and adjacent text alternative.
  • Print/static fallback is readable.
  • Surrounding document layout remains stable.
  • Legacy information parity is signed off.
  • Category-specific concept limit is met or split is approved.


Risks and unresolved questions
Library/API risk
Mermaid diagram types and layout engines do not share identical capabilities. Pinning prevents surprise changes but requires a deliberate update cadence.
Pan/zoom utility risk
svg-pan-zoom is mature but has current touch/event issues. A touch qualification may select another small adapter without changing renderer contracts.
Export risk
Computed-style inlining and ID rewriting need fixtures for gradients, markers, masks, clip paths and external SVG editors. Native text is mandatory.
Performance risk
Rendering all 20 diagrams at once may be wasteful. IntersectionObserver and a renderer singleton must be measured on target hardware.
Information risk
Automatic layout cannot rescue overloaded visuals. Owners must approve splits and content parity before migration.
Governance risk
CDN use is appropriate for this spike, not automatically for production. Security review, SBOM, integrity policy and self-hosting are approval gates.



10. Clear decision statement
Recommended rendering approach:
Mermaid 11.15.0 as the default diagrams-as-code SVG renderer; Viz.js/Graphviz 3.27.0 only for approved compound/orthogonal hard cases.
Recommended layout engine:
Mermaid ELK for qualified layered flowcharts; Graphviz dot for fallback compound graphs; Mermaid-native layout for sequences/states.
Recommended zoom/pan mechanism:
One shared SVG viewport adapter, initially qualified against svg-pan-zoom 3.6.1; replacement allowed behind the same interface if touch gates fail.
Recommended SVG export mechanism:
Browser-side clone, transform removal, style inlining, CSS-variable resolution, ID namespacing/reference rewrite, sanitisation and Blob download.
CDN and version-pinning strategy:
Exact jsDelivr versions for the isolated spike; reviewed, checksum-pinned self-hosted copies for production.
Number of diagram libraries permitted:
Maximum two renderers. Pan/zoom is infrastructure, and ELK is a layout engine—not additional authoring surfaces.
Main technical risks:
Touch behavior, category-specific Mermaid variance, export fidelity outside browsers, dependency weight/security, and information overload that no renderer can fix.
Conditions before bulk migration:
Three production pilots pass all acceptance checks in target browsers, exported SVGs open independently, print/static fallbacks pass, performance is measured, dependency/security review approves pinned assets, and rollback references exist.
First pilot diagrams:
S03 Task Memory Packet architecture; F10 Evidence & Evaluation Loop; S05 Agile Team Swimlane.
Split/redesign before migration:
F00, F04, F06, F07, F10–F12, S01, S03–S05 and S07.
